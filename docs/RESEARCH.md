# System One модели: Jev, Laya, Clef и как собрать свою

*Состояние на 5 октября 2026. Источники перечислены в конце документа.*

## TL;DR

* **Jev** (TypeSafe AI, 15.09.2026) не генерирует текст. Он получает `state` и
  набор типизированных вопросов (`noul` да/нет, `choice` ≤ 255 вариантов,
  `score` 2–10 уровней) и за один проход отдаёт калиброванные вероятности по
  каждому вопросу. Задержка 70–500 мс, $0.042 за 1M входных токенов, выход
  бесплатный. Архитектуру TypeSafe не раскрывает: говорят только про
  «parallel sampler» и обучение RLCD.
* **Laya** (Convai) — открытая модель с тем же API, но устроена по-другому:
  энкодер ModernBERT-large (395M) с головой, обученной с нуля. Она быстрая
  (33 мс), но почти не умеет работать zero-shot (0.36 на typed-decisions) и
  требует дообучения. Это «собрать из блоков», и глобально это не Jev.
* **Clef** (Cloudflare, 01.10.2026) — открытый Jev-совместимый клон, сделанный
  именно так, как вы предлагаете: **берётся большая LLM (Qwen 27B / 9B),
  замораживается, используется только prefill, а сверху ставится небольшая
  голова со схемой (+ LoRA r=256)**. По заявлению Cloudflare, Clef выигрывает
  у Jev 7 из 10 бенчмарков.
* Наш разбор публичных улик (раздел 4) говорит, что Jev почти наверняка
  устроен так же: декодерная LLM, работающая только на prefill. State
  кодируется один раз, каждый вопрос идёт отдельной веткой, которая видит
  state и себя (отсюда лимит «state + самый длинный вопрос ≤ 32k»). Варианты
  ответа читаются головой или логитами меток, калибровка делается через RLCD
  (RL с proper scoring rules).
* **Что мы собрали — `jex`**: замороженная Qwen2.5-0.5B-Instruct +
  древовидная упаковка вопросов в один проход + verbalizer-prior + голова в
  духе Clef/Laya, обученная дистилляцией из Qwen2.5-1.5B (учитель) с
  RLCD-дообучением + async-движок (KV-кэш состояний, непрерывный
  микробатчинг, стриминг ответов, живые сессии) + Jev-совместимый HTTP API.
  Всё прогнано на CPU, результаты в разделе 7.

## 1. Что такое System One модель (на примере Jev)

Название отсылает к System 1 у Канемана: быстрое интуитивное решение вместо
рассуждения шаг за шагом. Модель отвечает на вопросы с закрытым множеством
ответов, которое задано до вызова. Поэтому выход нельзя распарсить
неправильно, а галлюцинировать в текст негде: текста просто нет.

**API** (`POST https://api.typesafe.ai/v1/systemone`, модель `jev-1.13.0`):

```json
{
  "model": "jev-latest",
  "state": {"opportunity": "link", "name": "Managed Postgres", "description": "..."},
  "questions": {
    "is_sponsor_inquiry": {"type": "noul", "instructions": "Does `description` ask to sponsor the site?"},
    "product_category":   {"type": "choice", "instructions": "What kind of product?",
                           "criteria": {"dev_tool": "Developer tools, hosting, APIs", "course": "...", "unrelated": "..."}},
    "message_quality":    {"type": "score", "instructions": "How specific is the request?",
                           "criteria": ["Generic template", "Mentions site but no concrete ask", "Concrete ask with timeframe"]}
  }
}
```

Ответ: `noul` → `{"noul": 0.99}`; `choice` → `choice`, `probabilities`,
`confidence`; `score` → `score` (матожидание номера уровня), `legend`,
`probabilities`, `confidence`; `usage.output_tokens` фактически не
тарифицируется.

**Заявленные характеристики**

| параметр | значение |
|---|---|
| контекст | 64k на запрос; **state + самый длинный вопрос ≤ 32k** |
| choice | до 255 вариантов |
| score | 2–10 уровней |
| вход | только текст (строка, JSON-объект или массив) |
| задержка | 70–500 мс end-to-end, обычно около 100 мс |
| цена | $0.042 / 1M входных токенов, выход бесплатный |
| лимиты | 100K tok/s, 80 req/s |
| обучение | RLCD (Reinforcement Learning for Calibrated Decisions) |
| дообучение под клиента | нет, только через `state` / `instructions` / `criteria` |

**Независимая оценка** ([arXiv 2609.37647](https://arxiv.org/html/2609.37647v1)):
37 датасетов, 346K запросов, всё вместе обошлось в $9.15, средняя задержка 0.36 с.
MMLU 91.8, Belebele (122 языка) 86.7, IMDB 96.5. ECE для choice 0.028, для
одиночного noul 0.052 (модель слегка недоуверена). Если задавать много
noul-меток сразу, ECE 0.168: модель переоценивает «yes». Selective prediction
работает: на Banking77 при покрытии 50% точность растёт с 79.7% до 96.3%.
Модель обходит Qwen3.8-27B на 27 датасетах из 37. Авторы находят признаки
запоминания MMLU и обращают внимание на резкую деградацию на
низкоресурсных языках.

**Ограничения:** не пишет текст и не объясняет решения. Арифметика,
подсчёты и даты, записанные текстом, ненадёжны. Ответ можно сдвинуть
инъекцией в state. Работает только там, где пространство ответов закрыто и
известно заранее.

## 2. Laya (Convai Innovations): открытая модель, но другой класс

* **Архитектура:** ModernBERT-large (395M, двунаправленный, полностью
  дообучен) + голова, обученная с нуля: 2 трансформерных слоя, option-marker
  scorer и act/escalate head. Всего 421M. Многоязычная версия собрана на
  mmBERT-base (322M).
* **Механизм:** у каждого варианта ответа есть свой токен `[MASK]`. Скрытое
  состояние на нём превращается в логит, затем softmax по вариантам вопроса.
  Пространство ответов задаётся в запросе, переобучение не нужно.
* **RLCD в описании Laya:** политика сообщает распределение, для
  исследования к логитам добавляется гауссов шум, награда — строго
  собственное правило оценки (log + spherical, а для порядковых вопросов
  ещё RPS). Обновления REINFORCE с групповым baseline в стиле GRPO; для
  многоходовых диалогов TD(λ=1).
* **Цифры:** 32.8 мс p50 на T4. Zero-shot на typed-decisions 0.362, то есть
  почти случайно. После дообучения 0.766. Выходит переуверенной, и без
  доменной temperature ECE 0.47.
* **Почему это «немного не то»:** у энкодера на 400M нет знаний о мире
  (никаких MMLU 90%), а новые схемы без дообучения он почти не решает. Это
  быстрый дообучаемый классификатор с Jev-API, а не универсальная модель
  решений.

## 3. Cloudflare Clef: ближайший открытый аналог Jev

* **Бэкбоны:** Qwen3.8-27B (Clef) и Qwen3.5-9B (Clef-flash), **заморожены**.
* **Inference:** «Qwen делает только prefill, затем допустимые варианты схемы
  оцениваются параллельно; шаг решения неавторегрессионный».
* **Голова `JointSchemaHead`**
  (по [`joint_schema_model.py`](https://huggingface.co/Cloudflare/clef)):
  1. *Evidence routing:* для каждого варианта строится запрос
     (контекстный вектор + лексическое представление + вектор вопроса),
     который cross-attention'ом смотрит на скрытые состояния всей
     последовательности;
  2. *Joint decoding:* представления полей (вопросов) уточняются
     трансформерными слоями с учётом сводки по вариантам, глобального
     вектора и эмбеддинга типа;
  3. *Логит* = лексический prior + σ(gate) · (cosine(field, option) + MLP[f, o, f·o, |f−o|]).
* **Промпт:** один chat-промпт со `STATE:` и блоками `FIELD n / ALLOWED OPTIONS`,
  `<think></think>` пустой, затем `JOINT SCHEMA DECISIONS:`. Все вопросы лежат в
  одной последовательности и видят друг друга, то есть изоляции нет.
* **Обучение:** LoRA r=256 + голова. Label-smoothed CE + Brier, затем RLCD
  как вторая цель (частичная награда за соседние порядковые уровни).
  Данные — синтетика с перестановками порядка полей, промптов и структуры
  схем.
* **Результаты:** медианная задержка 38.8 мс у flash и 209 мс у Clef против
  524 мс у Jev (замер Cloudflare на 43 бенчмарках, Jev включает сеть). MMLU
  90.3, Banking77 macro-F1 94.2. Плюс vision-энкодер и контекст 64k.

Вывод: подход «большая LLM → только prefill → голова над вариантами» уже
воспроизведён в открытом виде и даёт качество уровня Jev.

## 4. Предполагаемая архитектура Jev: разбор улик

TypeSafe архитектуру не публиковал. Ниже то, что следует из открытых фактов.

| улика | вывод |
|---|---|
| Лимит «64k на запрос, но **state + самый длинный вопрос ≤ 32k**» | Каждый вопрос обрабатывается как отдельная последовательность `state + вопрос` (позиции ≤ 32k), а 64k — бюджет упаковки. Это ровно древовидная схема: общий префикс + изолированные ветки. Если бы вопросы шли одной последовательностью, как в Clef, лимит был бы на сумму. |
| «Вопросы оцениваются **независимо и параллельно**»; «нет эффекта батчинга сверх шума сэмплирования»; 13 вопросов на одном state в 12.2× дешевле и в 10× быстрее 13 отдельных вызовов | State кодируется один раз (общий префикс/KV), вопросы друг друга не видят, и ответ не зависит от того, с какими вопросами он сгруппирован. |
| Задержка почти не растёт с числом вопросов и примеров (Jev-IDS: 0.31–0.34 с при k = 1…8 примеров) | Нет авторегрессионного декодирования: один prefill, время которого на типичных размерах съедают накладные расходы. |
| Платится только вход, выход бесплатный | Вычисления ∝ числу входных токенов (prefill). «Выходных токенов» нет: в лучшем случае это одна позиция на вопрос. |
| MMLU 91.8, Belebele на 122 языках, C-Eval 83.9 | Нужен большой предобученный LLM-бэкбон: энкодер на 0.4B такого не выдаёт (ср. Laya). |
| Цена $0.042/1M | При H100 ≈ $2–3/ч и MFU prefill ≈ 45% этих денег хватает на ≈ 2.7·10¹⁶ FLOP на 1M токенов, то есть ≈ 2.7·10¹⁰ FLOP/токен ≈ 2·N_active. Без маржи N_active ≈ 13B, с нормальной маржой 3–8B активных параметров. Вероятнее всего это MoE (вроде 30B-A3B) или плотная модель на 4–8B. Оценка грубая: цена может быть субсидированной. |
| `score` максимум 10 уровней | Уровни читаются однотокенными цифрами 0–9 (verbalizer по цифрам). |
| `choice` до 255 | Индекс в uint8 и/или маркер-токен на каждый вариант (как у Laya и Clef), а не метки-буквы. |
| «Parallel sampler», «шум сэмплирования» между запусками | Вероятности снимаются с логитов за один проход. Шум, скорее всего, от недетерминированных батч-ядер GPU (или от MC-оценки). |
| RLCD «за эпистемически честные вероятности» | RL со строго собственными правилами оценки (как у Laya и Clef). |
| Мульти-label noul переоценивает «yes» | Изоляция вопросов не исправляет базовые частоты. Отдельные бинарные вопросы, заданные пачкой, не видят друг друга и не могут «поделить» вероятность. |

**Итоговая гипотеза:**

```
            ┌──────────── общий префикс (state), кодируется 1 раз, KV-кэш ─────────────┐
 tokens:    [sys][STATE: ...........................................................]
            ├─ ветка q1: [QUESTION 1 + варианты][slot] ← видит state + себя
            ├─ ветка q2: [QUESTION 2 + варианты][slot] ← видит state + себя
            └─ ветка qN: ...                             (позиции каждой ветки начинаются после state)
 один prefill-проход (decoder LLM, вероятно MoE, ~3–15B активных параметров)
 → на каждый вопрос: логиты вариантов (маркер-токены/метки) → softmax → калибровка
 обучение: SFT/дистилляция на синтетических схемах → RLCD (proper scoring rules)
```

## 5. Как сделать свою модель: три пути

| | A. Собрать из блоков (Laya) | B. Большая LLM + переделка (Clef, jex) | C. Дистилляция |
|---|---|---|---|
| суть | энкодер (ModernBERT/mmBERT) + голова с нуля | замороженная LLM, только prefill, ветки вопросов, голова/verbalizer, опционально LoRA | учитель (большая LLM или reasoning-модель с CoT) размечает синтетические запросы распределениями, ученик A или B учится на них |
| знание мира и zero-shot | слабые | сильные, от LLM | наследуются от учителя |
| задержка | ~30 мс | 40–500 мс (зависит от размера) | как у ученика |
| данные | много разметки на домен | работает сразу, голова учится на тысячах примеров | генерируются учителем без ограничений |
| риск | плохо обобщается на новые схемы | нужен GPU под большой бэкбон | ошибки и переуверенность учителя (лечится калибровкой учителя на gold) |

**Рекомендация: B + C.** Это ровно то, что мы прототипировали:

1. Бэкбон — открытая instruct-LLM, замороженная (в проде Qwen3-8B/14B или
   MoE 30B-A3B: это сходится с ценовой оценкой Jev).
2. Каждый вопрос — изолированная ветка над общим state. Ответы получаются
   параллельно, асинхронно и независимо, а state кэшируется.
3. Zero-shot prior = логиты однотокенных меток вариантов в слоте ответа.
   Обучаемая голова (evidence routing + конкуренция вариантов + гейт к
   prior) стартует ровно с zero-shot и не может сделать его хуже на старте.
4. Дистилляция: учитель — самая сильная доступная модель. Лучше всего
   System 2 модель, которая рассуждает (CoT) и отдаёт распределение по
   вариантам: logprobs или частоты по k сэмплам. Учителя сначала
   калибруем температурой на gold. Ученик учится на смеси gold и
   распределений учителя (CE + Brier).
5. Финальная стадия — RLCD: гауссова политика на логитах, награда log +
   spherical (+ RPS для score), групповой baseline. Затем temperature
   scaling по типам вопросов на dev.
6. Данные — синтетические схемы с перестановками вариантов, перефразировкой
   инструкций, случайными id и разным числом вопросов на state (как у
   Clef), плюс вспомогательные вопросы без gold, которые размечает только
   учитель.

## 6. Что собрано: `jex`

```
request ─► schema.parse ─► render: префикс [system][STATE] + ветка на вопрос
                                   (вопрос, строки вариантов A./B./…, слот ответа)
        ─► packing: древовидная маска (ветка видит префикс и себя),
                    позиции ветки = len(prefix) + i
        ─► backbone (frozen LLM, prefill only, без генерации)
              • prior: логиты меток вариантов в слоте ответа (verbalizer)
              • answer_hidden, option_hidden (среднее по строке варианта), memory
        ─► head (опционально): evidence routing → self-attn по вариантам → MLP; logits = s·prior + σ(g)·residual
        ─► temperature по типу ─► softmax ─► ответ в формате Jev
```

**Три уровня асинхронности**

1. *Внутри запроса.* N вопросов дают N изолированных веток в одном проходе.
   Математически это эквивалентно N отдельным вызовам (проверено тестами,
   расхождение ~1e-5): добавление, удаление и перестановка вопросов не
   меняют чужие ответы.
2. *Между запросами.* `AsyncEngine` держит LRU KV-кэш состояний. Вопрос можно
   прислать в любой момент. Пока идёт текущий проход, в очереди копятся
   новые вопросы, и следующий проход упакует их все (continuous
   micro-batching). У каждого вопроса своя future, ответы стримятся в
   порядке готовности. Модель крутится в отдельном потоке, event loop не
   блокируется.
3. *Живое состояние.* `open_session` / `append` / `ask_session`: state растёт
   (лог игры, чат, телеметрия), и вычисляются только новые токены. Порядок
   соблюдается: вопрос видит ровно те события, которые были добавлены до
   него.

**Отличия от Clef:** вопросы строго изолированы (как, судя по лимитам,
сделано у Jev), поэтому их можно кэшировать и досчитывать по одному. Голова
работает поверх готового zero-shot prior, а учитель перед дистилляцией
калибруется.
